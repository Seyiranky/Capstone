Isoko: a skills-to-income marketplace for young people in Kigali

Technical report, Final Version of the Product · Seyi Adebayo · BSc Software Engineering, African Leadership University · 23 October 2026
Live app isoko-web.onrender.com · API isoko-api.onrender.com · Code github.com/Seyiranky/Capstone · Video: VIDEO LINK · Demo sign-in: grace@isoko.demo, eric@isoko.demo, admin@isoko.demo, password password123

Isoko lets young workers in Kigali prove a practical skill and earn from it. A worker submits evidence of a skill. A peer reviewer, drawn at random and unrelated to the worker, checks it. Clients post jobs and receive candidates ranked by distance, trust and skill fit, each with its reasons. The client pays through MTN Mobile Money, and the payment produces a public receipt. This report compares the product with the approved proposal (FR-1 to FR-14, NFR-1 to NFR-8, RQ1 to RQ3). It then describes how the product works, how it was tested, and the engineering practices behind it.

Changes from the proposal, and why

  • Mentors became peer reviewers. Workers with verified skills in a category review others in it, and admins act as fallback. The proposal budgeted about four mentors, too few for a random draw to mean anything: with four reviewers a worker can often predict who will review them. A larger pool of peers makes the draw (FR-5) a real defence. Disclosure (RQ1 method) is kept in two forms. A reviewer can recuse with a reason ("I know this worker", "conflict", "not qualified"). The draw also automatically excludes past collaborators.
  • No reviewer–worker messaging (FR-12). A private channel between a worker and the person judging them is exactly the collusion route RQ1 must close, so reviewers stay anonymous. The human relationship the proposal wanted is kept in other ways: worker–client messaging, and apprentice seats, in which an experienced worker brings a newcomer onto a paid job and can endorse them.
  • Airtel Money was not integrated. Effort went into making one provider work end to end against its real sandbox. Payments sit behind a PaymentAdapter interface, so Airtel is one additional class.
  • Providers substituted. Pindo replaced Africa's Talking for SMS, being Rwanda-based and live. Brevo replaced SendGrid for email: it sends without an owned domain, and its HTTPS API works where the host (Render) blocks SMTP.
  • Escrow was tried and removed. With payment taken before the work began, a receipt appeared the moment a job was marked done, which read as if nobody had paid. The flow is now: the worker says the job is finished, the client marks it done and pays, then the receipt is issued.
  • Built beyond the proposal:
    • for workers: safe visits with check-in and SOS to a trusted contact, signed skill passports, signed income statements (PDF), and levels with public criteria;
    • for clients: rate guidance from real payments, and optional job cover (micro-insurance);
    • for the platform: crews and apprentices, a dispute process, a help centre, a live Fairwork score, an offline queue, and an installable PWA.

2. Technical functionality

Architecture. The web app is a React 18 + TypeScript single-page app (Vite, Ant Design, Redux Toolkit, react-i18next), installable as a PWA. It talks to an Express 5 + TypeScript API over JSON and Socket.IO, which carries live messages and notices. The API stores data in PostgreSQL through Sequelize: 32 models and 72 migrations. A background sweep every 10 minutes re-checks unconfirmed payments with MTN, escalates overdue disputes, follows up safe visits and unanswered applications, reminds clients to mark finished work done, and closes resolved support requests. Deployment: the web app is a Render static site. The API runs on Render as a Docker web service in Frankfurt, built from Dockerfile.prod; on start it migrates and seeds an empty database. The database and private file storage are on Supabase (eu-central-1).

The core flow, front end to back end:

client posts gig → admin approves → ranking invites top workers / workers apply (eligibility checked) → client approves one → worker confirms → worker: "I've finished" → client marks done → POST /transactions/pay {phone} → MtnMomoAdapter.requestPayment → MTN /requesttopay (X-Reference-Id = our reference) → transaction "initiated" → MTN callback, or the sweep's status poll → SUCCESSFUL → transaction "confirmed" (once: idempotent) → payouts per worker share → public receipt with MTN's transaction id → both parties review → trust score recalculated

Data handling and logic. Each step is enforced on the server, not only hidden in the interface:

  • Eligibility. applicationEligibility.ts refuses an application that breaks a rule. A gig is sensitive when it involves children or work inside a home; for those it requires a reviewed skill in the trade, a confirmed phone and a record of past work.
  • Reviews and the review queue. Reviews need a confirmed payment. Reviewers never see another reviewer's verdict.
  • Uploads are checked by their content (magic bytes), hashed, and stored through a storage driver.
  • Errors. Invalid input is refused with a message, and the interface shows it. Examples: a wrong password; an empty or under-priced gig; a reviewer reviewing someone they know; a duplicate payment callback; a failed MTN payment such as INVALID_CURRENCY, which is shown to the client and lets them retry.

Fig. 1: a real payment through MTN's MoMo sandbox (20 Oct 2026). The adapter smoke test confirmed a request in 2.5 s and reproduced the failure path (docs/evidence/momo/README.md).

5. Code quality and technical implementation

Structure (NFR-6). The server code is layered:

  • 21 routers (about 140 endpoints);
  • middleware for authentication, roles, rate limits and upload checks;
  • controllers that read the request and shape the response;
  • 30 services, one per business area, holding the rules;
  • models, and a lib/ of drivers and utilities.

The web app is organised by feature, with pages loaded on demand and pure logic in src/lib where it can be unit-tested. Both sides use strict TypeScript. Quality checks:

  • ESLint runs with 0 warnings on both sides.
  • CI checks that the English and Kinyarwanda files hold the same keys.
  • CI also checks that code copied between the server and the client is identical.

Names follow the domain (completionService.reportWorkDone, paymentService.refreshPending). Comments explain why a rule exists, for example why the trust prior's strength is 3 and not 5. The history has 205 commits, each describing what changed and why.

OOP principleWhere it is applied
Abstraction and polymorphismPaymentAdapter (services/payments/adapter.ts) declares requestPayment, buildCallback, normaliseStatus and checkStatus. SimulatedMomoAdapter and MtnMomoAdapter implement it, so paymentService never knows which provider it holds. The same strategy pattern selects the SMS drivers (log, Pindo), email (log, SMTP, Brevo) and storage (local disk, Supabase) from configuration (open/closed principle).
InheritanceThe 32 models extend Sequelize's generic Model<Attributes, CreationAttributes>. HttpError extends Error carries an HTTP status from services to responses.
EncapsulationUser keeps its secret fields (password hash, tokens) out of every read. PdfDocument hides PDF byte offsets behind title, heading, table and toBuffer, producing receipts and statements with no PDF library. A safety-net balance is never stored: it is derived from its ledger, so it cannot drift.
Separation of concerns, reuseOne service per area (matching, verification, payments, payouts, disputes, trust…). Shared helpers: notify() covers all three channels; the eligibility rules are one module used by both the API and the web app.
AlgorithmProblem solved, and approachCost
Weighted match scoringDistance between worker and gig by the haversine formula, decaying by half every 3 km and cut off at 15 km. Combined with trust, skill fit (verified 1, pending 0.6, unverified 0.4) and availability, with weights 0.3/0.3/0.3/0.1 from a stored profile so RQ2 can compare weightings. Returns the reasons with the score. Ranked invitations keep places for newcomers (exploration slots).O(n log n)
Auditable reviewer drawFilters out ineligible reviewers: the worker themselves, past collaborators, disclosed relationships, earlier reviewers of the task, too-frequent pairings. Keeps the least busy, then picks one deterministically from a SHA-256 seed. The seed and every exclusion are stored, so an auditor can replay any draw (RQ1).O(r)
Collusion detectionFlags reviewers whose approval rate is more than 2 standard deviations from the mean (z-score, at least 5 reviews), decisions made in under 60 s, repeated pairings and prior job ties.O(d)
Bayesian trust scoreShrinks a worker's average toward a prior (mean 3.5, strength 3), and halves a review's weight every 180 days. Laplace smoothing keeps one completed job from reading as a 100% completion rate. One 5-star review cannot outrank twenty 4.8s.O(k)
Rate guidance25th percentile, median and 75th percentile of what a category actually paid, falling back to posted budgets below 3 payments and saying which basis it used. Counters undercutting.O(m log m)
Block randomisationPermuted blocks (Fisher–Yates shuffle) assign pilot participants to study arms, which never drift apart by more than half a block.O(1) per claim

6. Limitations and next steps

  • Pilot. RQ1–RQ3 are not yet answered with real users. The 25–30 person pilot, including the RQ3 paired survey, is the next phase, and the instruments for RQ1 and RQ2 are built.
  • Payments. MTN runs in its sandbox (EUR test money; no prompt reaches a real phone). Going live needs an MTN production agreement through a registered business. Airtel is one adapter away.
  • Kinyarwanda notices. Server notices should be translated through a catalogue in the notification layer (NFR-1).
  • Code structure. skillTaskController.ts (755 lines) and adminController.ts (589 lines) still hold logic that belongs in services.
  • Hosting. The free tier is far from users. A host in or near Rwanda would cut most of the 286 ms round trip.
